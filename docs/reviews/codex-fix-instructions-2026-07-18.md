# تعليمات Codex لفحص وإصلاح مستودع Muharrir

**التاريخ:** 18 يوليو 2026  
**المستودع:** `3ssiri/muharrir`  
**الغرض:** تزويد وكيل برمجي بخطة تنفيذ واضحة لفحص المشروع، إصلاح المشكلات الفعلية، والتحقق من جاهزيته للإصدار دون تغييرات عشوائية أو كسر دعم الويب وTauri.

## 1. قواعد العمل الإلزامية

1. اقرأ `AGENTS.md` كاملًا قبل تعديل أي ملف.
2. لا تفترض أن المشروع ما زال في مرحلة التحويل إلى Tauri؛ التحويل مكتمل.
3. حافظ على تشغيل المشروع في بيئتين من الكود نفسه:
   - متصفح Next.js بتصدير ثابت.
   - تطبيق سطح مكتب Tauri v2.
4. لا تنشئ API routes أو middleware لأن التطبيق مبني على `output: 'export'`.
5. أي استدعاء لواجهات Tauri يجب أن يمر عبر `isTauriApp()` مع مسار بديل للمتصفح.
6. لا تخزن مفتاح API في `localStorage` داخل Tauri. يجب استمرار استخدام OS Keychain.
7. لا تضف نصوصًا ظاهرة مباشرة داخل JSX. أضف مفاتيح متطابقة إلى:
   - `src/i18n/locales/ar.json`
   - `src/i18n/locales/en.json`
8. استخدم أنواع `UiMessage` و`ToolInvocation` بدل `any` عند التعامل مع الرسائل.
9. استخدم `log.*` بدل `console.*`.
10. لا تغيّر السلوك أو الواجهة لمجرد إعادة الهيكلة؛ كل تغيير يجب أن يعالج عطلًا مثبتًا أو مخاطرة واضحة.

## 2. مرحلة خط الأساس

نفّذ الأوامر التالية وسجّل النتائج قبل أي تعديل:

```bash
node --version
npm --version
npm ci
npm run lint
npm run test:unit
npm run build
cargo check --manifest-path src-tauri/Cargo.toml
```

ثم شغّل اختبارات الواجهة بالطريقة الصحيحة لأن `webServer` معطل في إعداد Playwright:

```bash
npm run dev
# في طرفية ثانية
npm test
```

لا تعتبر المهمة ناجحة إذا تعذر تشغيل اختبار بسبب غياب بيئة أو سر. صنّف النتيجة صراحة إلى:

- فشل فعلي في الكود.
- فشل إعداد محلي.
- سر أو صلاحية غير متاحة.
- اختبار غير حتمي أو هش.

## 3. فحص ترقية التبعيات الأخيرة

المستودع رُقّي مؤخرًا إلى Next.js 16 وnext-intl 4 وVitest 4 مع تفعيل CSP. افحص تحديدًا:

1. توافق جميع إعدادات Next.js مع التصدير الثابت.
2. عدم استخدام API قديم من `next-intl`.
3. توافق إعداد Vitest والـ mocks والـ environment مع الإصدار 4.
4. عدم وجود تحذيرات hydration أو أخطاء route generation للغتين.
5. توافق React وTypeScript وESLint مع الإصدارات المثبتة.
6. أن `npm run build` ينتج مجلد `out/` صالحًا لتغذية Tauri.
7. أن نسخ PDF worker يحدث قبل التشغيل والبناء ولا يعتمد على مسار خاص بنظام تشغيل واحد.

لا تخفّض الإصدارات تلقائيًا. أصلح الاستخدامات غير المتوافقة أولًا، ولا تقترح downgrade إلا مع دليل أن الخلل upstream ولا يوجد إصلاح آمن.

## 4. فحص CSP والأمان

راجع سياسة Content Security Policy في الويب وTauri وتأكد من أنها تحقق التوازن بين المنع والتشغيل:

- لا تستخدم `*` للمصادر دون ضرورة موثقة.
- لا تضف `unsafe-eval`.
- قلّل `unsafe-inline` أو أزلها حيث يمكن دون كسر التطبيق.
- اسمح فقط بعناوين مزودي النماذج الضرورية، مع مراعاة أن المستخدم قد يضيف مزودًا يدويًا أو محليًا.
- افحص `connect-src` لاتصالات OpenAI-compatible وAnthropic والمزود المحلي.
- امنع تحميل محتوى تنفيذي من ملفات المستخدم المرفوعة.
- تحقق من عدم تسجيل مفاتيح API أو رؤوس Authorization أو محتوى حساس في السجلات.

افحص أيضًا:

- التحقق من `baseUrl` قبل الطلبات.
- منع البروتوكولات غير الآمنة افتراضيًا، مع استثناء واضح ومقصود لـ `localhost` و`127.0.0.1` عند استخدام مزود محلي.
- مهلات الشبكة والإلغاء عبر `AbortController`.
- تحديد حجم الملفات المرفوعة قبل تحليل PDF وDOCX.
- التعامل الآمن مع الملفات التالفة أو المضغوطة بشكل ضار.

## 5. فحص مزودي النماذج

راجع المسار كاملًا من شاشة الإعدادات حتى `chat-client.ts` و`tauri-bridge.ts`:

1. OpenAI-compatible providers.
2. Anthropic provider الأصلي.
3. المزودون المحليون الذين لا يحتاجون مفتاح API.
4. اختبار الاتصال من المتصفح ومن Tauri.
5. اختلاف تنسيق الأخطاء والاستجابات بين المزودين.
6. Streaming والتوقف والإلغاء وإعادة المحاولة.
7. رسائل الخطأ المترجمة للمستخدم.

معايير القبول:

- لا يُطلب مفتاح API لمزود محلي معلّم بأنه بلا مفتاح.
- لا يُرسل حقل Authorization فارغًا أو وهميًا.
- لا تفشل واجهة الإعدادات إذا أعاد المزود قائمة نماذج فارغة.
- تُصنف أخطاء 401 و403 و429 و5xx والشبكة بدقة.
- لا تتحول أخطاء المزود إلى رسالة عامة تخفي السبب القابل للإصلاح.

## 6. فحص تدفق الأدوات والبث

راجع:

- `src/lib/chat-client.ts`
- `src/lib/chat-stream.ts`
- `src/lib/format-validator.ts`
- `src/app/[locale]/page.tsx`
- مكوّنات عرض الأدوات الثلاث.

تحقق من:

1. أن parser يتعامل مع أجزاء البث المجزأة بين عدة chunks.
2. عدم فقدان UTF-8 العربي عند حدود chunks.
3. عدم تكرار tool call أو tool result عند إعادة التصيير.
4. إنهاء حالة loading عند الإلغاء أو الخطأ.
5. عدم بقاء الرسالة النشطة في حالة streaming بعد انتهاء الاتصال.
6. تحقق Zod من جميع وسائط الأدوات قبل العرض.
7. حلقة التصحيح لا تتجاوز ثلاث محاولات ولا تغير المعنى.
8. نموذج التصحيح قابل للتهيئة أو له fallback واضح إن لم يكن متاحًا لدى المزود.
9. فشل أداة واحدة لا يفسد سجل المحادثة كاملًا.

أضف اختبارات وحدة للحالات الحدية، خصوصًا:

- JSON مقسوم بين chunks.
- Unicode عربي مقسوم بين chunks.
- tool call ناقص.
- stream ينتهي دون marker نهائي.
- إلغاء المستخدم للطلب.
- 429 ثم نجاح إعادة المحاولة.

## 7. التخزين والترحيل

راجع Zustand وDexie وعمليات التصدير والاستيراد:

- لا تفقد الإعدادات الحالية بعد تغيير schema.
- أي migration يجب أن يكون idempotent.
- لا تُصدّر مفاتيح API افتراضيًا.
- الاستيراد يتحقق من schema ولا يثق بالملف مباشرة.
- لا يمكن لملف استيراد خبيث الكتابة خارج البنية المتوقعة.
- تعامل مع quota exceeded وIndexedDB unavailable برسالة مفهومة.
- اختبر الانتقال بين نسخة قديمة وحديثة من بيانات `prompt-iterator-storage`.

## 8. Tauri وRust

نفّذ فحصًا خاصًا للآتي:

1. أوامر keyring الأربعة وعدم تسريب القيم في الأخطاء.
2. `test_api_connection` والمهلة والتحقق من URL.
3. صلاحيات Tauri والـ capabilities وعدم منح صلاحيات أوسع من الحاجة.
4. system tray والاختصار العام وتعارضه مع اختصارات النظام.
5. close-to-tray وإمكانية الخروج الفعلي.
6. updater الموقّع وسلوك غياب مفاتيح التوقيع محليًا.
7. اختلافات Windows وmacOS وLinux في keyring والمسارات والأيقونات.
8. عدم استخدام `unwrap()` أو `expect()` في مسارات يمكن أن تتأثر بمدخل المستخدم أو النظام.

نفّذ:

```bash
cargo fmt --manifest-path src-tauri/Cargo.toml -- --check
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets --all-features -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml
```

## 9. الواجهة وإمكانية الوصول

افحص باللغتين العربية والإنجليزية:

- اتجاه RTL/LTR.
- التنقل بلوحة المفاتيح.
- focus trap في الحوارات.
- أسماء الأزرار والأيقونات لقارئات الشاشة.
- contrast والحالات disabled/loading/error.
- عدم قفز التخطيط أثناء البث.
- عرض النصوص الطويلة والكود والروابط.
- عرض رسائل الخطأ دون قص.
- Spotlight واختصارات لوحة المفاتيح وعدم تعارضها مع حقول الإدخال.

لا تستخدم اختبارات snapshots وحدها. أضف assertions سلوكية للمسارات الحرجة.

## 10. GitHub Actions والإصدارات

راجع workflows وتأكد من:

- تثبيت نسخ Node وRust بوضوح.
- استخدام `npm ci`.
- تشغيل lint والوحدة والبناء قبل حزم Tauri.
- عدم كشف الأسرار في logs.
- عدم محاولة بناء إصدار desktop beta عندما تقضي السياسة الحالية بتجاوزه.
- أن تاج `v*` فقط يشغّل إصدار سطح المكتب المقصود.
- فصل فشل التوقيع عن فشل compilation.
- رفع artifacts بأسماء واضحة لكل نظام ومعمارية.
- استخدام caching دون إعادة استخدام artifacts غير متوافقة.
